## Choices and remaining limits

Kernel `flock` replaces PID-based stale-owner detection for harness and project provisioning. The lock files live in container-local `/tmp`, so a recycled container cannot restore a stale PID. An old build still running across a deployment uses the old lock path and does not coordinate with the new one. This transition has not been measured on Cloudflare.

For clone and removal, a successful shell exit is not enough. The Workspace Host requires Computer's post-command sync to complete with no skipped entries and checks the durable store. A failed removal still drops the catalog row and thread, but reports `workspace: "failed"`. Nothing retries a pending copy. Computer can apply only some batches before reporting pending, so the clone markers do not prove all Git objects or working-tree files survived. A partly copied clone can reappear after eviction; [GitHub connection](design/github-connection.md#partial-copies) gives manual checks and requires owner approval before deleting files. The per-instance Supervisor queue and the shell lock do not prove ordering across eviction and post-command sync. A paid Computer test is needed for that boundary.

The size guard keeps the existing fail-open rule for a failed measurement. It checks the default branch before a new clone, not a repository already present in the workspace. A disconnected project whose old clone remains may reuse that clone, including uncommitted work. These limits are deliberate here to avoid deleting owner files or changing credential ownership without evidence. The Supervisor never receives the device-flow token.
