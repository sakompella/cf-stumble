# Computer integration

cf-stumble uses Cloudflare Computer release 0.10.0: `@cloudflare/computer` from npm, source commit `bb0a5db4b7e8c8a79625d63e0e272602f909640e`, and image `ghcr.io/cloudflare/computer-computerd-linux-x64@sha256:6ec793fa80f109acf8b3cd4e295284cfed97f61c03030b780a612ec22c49b294`. ADR-0026 records the decision. The workspace image builds `computerd` from that commit with `infra/workspace-image/computerd-walk.patch` applied. ADR-0042 records why the walk is patched.

The Workspace Host runs the container through `ContainerBackend`, with the container scheduled by the Host's Durable Object. The instance size is `WORKSPACE_CONTAINER_INSTANCE` in `infra/worker-settings.ts`, and the image is the `app` Container that `infra/alchemy.run.ts` attaches to the `WorkspaceHost` Durable Object class. Upgrade the package, the commit and the image together, and adopt a newer release only if the full application workflow passes against it.

The workspace image is built once in CI and published to GitHub Container Registry as `ghcr.io/sakompella/cf-stumble-workspace:<hash>`. The deploy and every machine that runs the container pull it, and nothing builds it locally.

The Workspace Host has two exec backends. The container handles Node, pnpm, TypeScript compilation, tests, and project commands. The isolate backend runs just-bash in a Dynamic Worker with Git over the SQLite workspace, so it handles text operations and Git without waking the container; it has no Node, pnpm or `gh`, and its only network use is Git fetch, pull and push to GitHub over HTTPS with the token from the `gh` hosts file (`src/workspace/project/git-fs.ts`), plus `curl`. The shell module set ships the `@cloudflare/computer/shell/curl` group (`tools/build-shell-modules.mts`), and the shell's `ShellWorker` subclass routes its fetch through the `EGRESS` binding, an `IsolateEgressGateway` entrypoint the Host constructs from `ctx.exports` (`src/workspace/project/isolate-egress.ts`). The gateway forwards any method to any http(s) host and passes the request's headers and body through unchanged, and follows redirects itself (max 5). As `fetch` does, a redirect hop to another origin drops the caller's `Authorization` and `Cookie` headers for the rest of the chain. For api.github.com only, the gateway adds `Authorization: Bearer <token>` with the workspace's GitHub token, which it reads on the Host side from the `gh` hosts file (or the `GH_TOKEN` secret when the hosts file has none), and only when the request carries no Authorization header of its own; the token never reaches the isolate, is sent to no other origin, and a redirect hop off api.github.com drops it. The dynamic worker itself keeps `globalOutbound: null`; only the shell's fetch reaches the gateway. The isolate is the only writer of `.git`. Git forms the isolate does not support exit 129 and run in the container: an isolate exit of 127 or 129 before any stdout reruns the command there (`src/workspace/project/exec-fallback.ts`), and a kill during that switch starts no container, or kills the one already starting. A just-bash execution limit reruns there too: an exit of 126 whose stderr carries a limit message (iteration, recursion, output, command-count or any other `limit exceeded` wording), or an exit of 124 with an execution-deadline message, while a plain 126 such as permission denied stays an isolate result. There, `git` is a wrapper (`infra/workspace-image/git-readonly.sh`, installed as `/usr/local/bin/git`; real Git stays at `/usr/bin/git`) that runs read-only subcommands and `clone` into a new directory with `GIT_OPTIONAL_LOCKS=0`, and forwards every other form to the Host. The wrapper (`infra/workspace-image/git-forward.mts`) runs the repository's `pre-commit` and `commit-msg` hooks in the container as real Git would (unless `--no-verify` or `-n`), then POSTs `{argv, cwd}` to `http://computer.internal/api` with the bearer token in `CF_STUMBLE_GIT_TOKEN`. `WorkspaceProxy` in `@cloudflare/computer` only passes `/health` and `/api` to the Host, so the route is `POST /api`; the container's own `/api` is a GET websocket upgrade. The Host (`src/workspace/git-forward.ts`) compares the token with the one it keeps in storage (`gitForwardToken`), pulls the container's disk changes into the workspace, runs the isolate Git client, pushes the result back, and answers `{stdout, stderr, exitCode, gitDir, state}`, where `state` holds hashes of `.git/HEAD`, `.git/index` and the current ref file. The wrapper waits (20 s, `CF_STUMBLE_GIT_WAIT_MS`) until the container's `.git` files match `state`, prints the output and exits with the code, so a `git add && git commit` in one command works and an isolate read right after sees the commit. Forms the isolate does not support exit 129 with the plain message; the isolate fallback sets `CF_STUMBLE_GIT_FALLBACK=1`, and a container with no token keeps the old refusal. The token reaches the shell as `COMPUTER_VAR_CF_STUMBLE_GIT_TOKEN` in the container environment. A provider machine cannot intercept `computer.internal`, so there the wrapper reports the connection failure. cf-stumble's own container scripts that must still write set `CF_STUMBLE_CONTAINER_GIT_WRITE=1`: the `core.fileMode` setting after a large project's container clone, and `gh auth setup-git`. `src/workspace/project/git-cli.ts` makes the output of the common forms match real Git: `status` (long, `-s`, `--porcelain`, `-b`, with upstream ahead and behind counts and the index and worktree columns that `@cloudflare/computer` swaps fixed), `commit` (`[main abc1234] subject`, the change counts and the `create mode` and `delete mode` lines; `--no-verify` and `-q` accepted), `checkout` and `switch` messages, `checkout -- <paths>` (run as `restore`), `branch`, `branch -v` and `-vv` (with the detached HEAD line), the `reset` messages, and the forms `add .`, `add -u`, `reset --soft`, `reset --mixed`, `restore --staged` and `push origin :branch`, and the global options `-c user.name=...`, `-c user.email=...` and `--no-pager`. Abbreviated object names are always 7 characters. `git clone` of a `https://github.com/` URL sends the same token. A `bash` call that names no backend runs in the isolate when every program in it is one the isolate has and the command touches no absolute path outside `/workspace` (`/dev/null` is exempt: the isolate's shell serves it as a virtual device), and in the container otherwise; its optional `backend` parameter forces the container (`src/workspace/project/exec-selection.ts`). The shell's modules ship as the static asset `ASSETS` and are loaded into the Dynamic Worker. The Host passes its workspace stub with each exec call (`src/workspace/project/isolate-shell.ts`). The shell must not open a new request back into the Host to get it: every exec of a turn runs inside the Host's `project()` call, each new request back into the Host counts toward the runtime's subrequest depth limit, and with such a request per exec every forced-isolate exec after the 13th in a turn failed with `Subrequest depth limit exceeded`.

The isolate's Git sets `core.fileMode=false` in every repository it creates. `git init` writes it because the Computer Git library probes the SQLite workspace and finds it cannot store the executable bit (it also writes `core.symlinks=false` and `core.ignorecase=true`); real Git does the same on a filesystem like that. An isolate clone and a container clone get the same setting on purpose, so a mode-only change never shows in `status`. The cost is that a `chmod` shows in neither `git status` nor `git diff`, which differs from real Git on Linux. The isolate also runs `checkout --detach`, `checkout -B`, `push -u`, `mv` and `log -- <path>`, and refuses forms it does not know with exit 129, so the container's Git runs them (`src/workspace/project/exec-fallback.ts`).
The Workspace caps what a command's output keeps: the last 2,000 lines or 64 KiB of each stream, whichever the output hits first (`WorkspaceOptions.output` in `src/workspace/workspace-platform.ts`, limits in `src/workspace-layout.ts`). The event stream between the Worker and the harness still carries the whole output, and the harness keeps only the tail it shows the model. When the Workspace saved a stream in full, the terminal event names the file under `/.cf-stumble/output`, the bash tool reports it as the spill path, and the model can read the file to see what the tail left out. The directory keeps the newest 50 saved files and sits outside `/workspace/projects` and `/workspace/harness`, so saved output never lands in a repository and old files cannot fill the disk.

## Workspace layout

One durable Computer workspace holds the owner's harness repository and the connected GitHub project repositories, each in its own directory with its own Git history. The page selects the project directory a turn starts in, but the shared filesystem is not a security boundary between the repositories.

Each project's conversations live in the serving facet's Pi Durable storage, outside the workspace and outside generation state (ADR-0048). Starting a fresh thread points the project at a new conversation without changing project files. The conversations and the workspace both survive generation changes.

The workspace name comes from the tenant and nothing else. The Worker reaches one Supervisor by a constant name, and the Supervisor derives its one workspace name from that, so harness builds and every project reach the same container.

`src/workspace-layout.ts` owns the layout:

| Path                               | Holds                                                                               |
| ---------------------------------- | ----------------------------------------------------------------------------------- |
| `/workspace`                       | The workspace root. Every addressed path lives beneath it.                          |
| `/workspace/AGENTS.md`             | The managed instructions, above every repository.                                   |
| `/workspace/harness`               | The owner's editable harness checkout.                                              |
| `/workspace/.config/gh`            | `gh` configuration, including the GitHub credential (`hosts.yml`).                  |
| `/workspace/.gitconfig`            | Git's global configuration, including the `gh` credential helper.                   |
| `/workspace/projects/<project id>` | One connected project's clone.                                                      |
| `/tmp/cf-stumble-builds/<commit>`  | Build scratch for one labeled commit, outside `/workspace`. It holds no repository. |

The workspace behaves like an ordinary development machine: unrestricted outbound internet, `git`, `gh`, and repository toolchains. GitHub credentials live in `gh` and Git configuration under `/workspace`, so they survive a container replacement.

cf-stumble owns `/workspace/AGENTS.md`. Whenever a run asks for a project capability, provisioning calls the Workspace Host's `ensureManagedInstructions`, which writes the current text over whatever file is there. An instruction change reaches the workspace at the first run after a deploy, and an edit to the file lasts only until the next run. The Host refuses the write when the workspace root or the file is a symbolic link, or the path is a directory. Provisioning never writes a repository's own `AGENTS.md`.

### Resets and fresh threads

A workspace reset would delete files under a running command, so the Supervisor refuses it with HTTP 409 `run-active` while a run is active, and a project disconnect the same way. A run is active from when the facet reports its conversation running until the facet reports it settled, or until its own deadline passes. The facet reports each running conversation with its run, the first input submission Pi placed for it, so a queued follow-up that starts in the same commit as the previous run ends is a new run: the Supervisor ends the previous run's workspace capability and gives the follow-up its own deadline. A fresh thread is allowed during a run: it aborts the project's current conversation and points the project at a new one. Submitting a message, opening a conversation, starting a fresh thread, and a disconnect that releases the pointer each run one at a time per project (`ProjectThreads`, in memory), and each re-reads the project inside that turn, so a message checked before a disconnect never gives the disconnected project a new conversation. The Host also refuses a reset with HTTP 409 `workspace-busy` while it runs a build, provision, removal, managed-instructions write, or credential install.

From the moment a reset reaches the Supervisor until the Host answers, the Supervisor refuses a new message, a connect or disconnect, a project capability, and a second reset with `workspace-busy`. The Host applies the same exclusion for the same span: its operations refuse without running (a file change answers `workspace-busy`, a credential install `workspace-unavailable`), a project capability request throws, and a second reset answers `workspace-busy`. Both exclusions live in memory, one per object instance.

### Turn capability

A project's conversation runs in that project's directory. The project capability addresses the whole workspace, so the agent can read a sibling repository or the managed instructions, and the path guard is the workspace root, read from `WORKSPACE_ROOT` in `src/workspace-layout.ts` by both the guard and the path translation.

A run asks the Supervisor for a capability through its host's `workspace`, naming its conversation, and the capability lasts only as long as that run. The Supervisor refuses a conversation whose run it has no record of or whose deadline has passed. The Supervisor asks the Host for it with the run's remaining time before its deadline, so the Host ends it at the deadline, and the Supervisor ends it again when the run settles. After that, `lstat`, `readFile`, `writeFile`, and `startExec` answer `turn-ended`, also through a duplicate the generation kept, so a generation that ignores the end of its run cannot keep editing the workspace while a later run works. A refused call does not count as workspace activity, so late calls cannot keep the idle container running. `kill` and `endTurn` still answer. A container replacement refuses only the next command of a live run, with `container-restarted`, and file calls go on because the files are durable (`src/workspace/project/target.ts`). The capability owns that acknowledgment: when the command that connects to the new container is the one that reports `container-restarted`, the capability counts that as the refusal and the next command runs.

The generation's `ExecutionEnv` (`src/facet/generation-1/execution-env.ts`) calls only this capability. It implements only the members that the installed tools (Pi Durable 1.5.0's coding tools) and the prompt call. Every other member answers a `not_supported` `FileError`, and the optional `listFiles` is left out. The capability has no open file handle, so a binary reader reads the whole file into memory when it opens, which limits it to `MAX_FILE_BYTES`.

When you bump Pi Durable, search the new version for calls to the members that file stubs out before you deploy, and implement any member it now calls:

```sh
cd node_modules/@earendil-works/pi-durable/dist && rg -n -g '*.js' -g '!storage/jsonl' -g '!testing' \
  '\.(readBinaryFile|appendFile|openTextLineReader|readTextLines|truncateFile|flushFile|renameFile|listDir|openDirReader|watch|createDir|remove)\('
```

In 1.5.0 it finds only Pi's own Node environment calling itself (`env/node.js`), a doc comment in `harness/transcript.js`, and two unrelated `watch` methods in `harness/harness.js` (the host's views and the task graph).

A generation must also speak the Supervisor's current facet-to-Supervisor protocol. `FACET_COMPATIBILITY` in `src/facet/runtime-contract.ts` is `pi-durable@<version>/host-<N>`, the facet reports it from `compatibility()`, and the startup check, activation and rollback compare it exactly. Bump `host-N` when the facet-to-Supervisor RPC contract changes: a host call the facet makes (`arm`, `running`, `workspace`) or a facet method the Supervisor calls. A Pi Durable bump changes the key by itself. An optional trailing argument, such as the `failed` map that `running` carries, leaves the key alone: an older facet omits it and an older Supervisor ignores it.

## Harness execution

The harness source is TypeScript, while Dynamic Workers need Worker-executable modules. Computer builds a canonical module map for a labeled harness commit. The Supervisor validates it and stores it in R2 under that commit, so nothing rebuilds to serve or roll back. ADR-0028 defines the artifact. The Supervisor names the serving Worker Loader entry by the commit ID and the serving instance (ADR-0027), because Loader names are cached with their `env`, and a changed commit or a replaced instance must not reuse an old entry.

### Build isolation

A build extracts its commit into `/tmp/cf-stumble-builds/<commit>` and clears that directory first. The path is container-local, outside `/workspace`, and holds no checkout, so clearing it destroys nothing. The harness directory is the owner's editable clone. The build's provision step runs on the Workspace Host with the isolate Git client, not in the container (`src/workspace/harness-provision.ts`): it clones the harness at depth 50 through a staging directory when it is missing, refuses rather than deletes a populated directory that is not a repository, and refuses a checkout whose origin is another remote. It deepens the fetch (depth 500, 5,000, then 100,000) until the pinned commit is present, because isomorphic-git cannot fetch a bare commit ID, and otherwise fails with `harness commit <commit> is not in <remote>`. A checkout with no local tracked changes is fast-forwarded to its upstream; one with changes is left as it is, with a message. One provision runs at a time per Host (a semaphore in `ComputerWorkspaceOperations`). The later `checkout` step only reads the repository with `git archive` in the container. `HarnessArtifacts` (`src/supervisor/artifacts/index.ts`) admits one build per commit at a time, and a second request for a commit already building joins that build, because two builds of one commit would clear each other's directory.

### Build phases

The Supervisor's build runs `HARNESS_BUILD_CONFIGURATION.buildPhases` (`src/harness-build.ts`) in a directory `git archive` just wrote, which has tracked files only: a production install (`--prod`) from `pnpm-lock.yaml`, then a build of the module map. The build needs only the runtime packages and `esbuild`, which is a production dependency for that reason, and Node runs the build script with its own type stripping. Each phase is its own Durable Object RPC with its own exit code, output capped by the Workspace's output limits, and `WORKSPACE_COMMAND_TIMEOUT_MS` timeout, because one long command died three times with no sign of which phase had been running. The publish step copies the module map to a file of its commit's own (`/workspace/.cf-stumble-build-output/<commit>.json`), so two commits published at once never read each other's map, and a discard removes only that file.

A fresh build container needs pnpm, which downloads the version `package.json` pins on first run; Node 22; `registry.npmjs.org`; and `git` and `tar` for the archive. The Host's isolate reaches `github.com` over HTTPS for the clone and fetch. A developer machine hides most of these.

The release proof is two clean Computer builds of one labeled commit.

## Paid probes

Probes that run on the disposable paid Cloudflare account are approved. A local container run proves tool availability and build behavior, not deployed-platform behavior, and a report must not claim otherwise. A probe that cannot run states the blocker instead of reporting a simulated result as real.

## Container lifetime

The container does not stop by itself while the Workspace Host exists. Computer's backend accepts the WebSocket that computerd opens back to the Host, and nothing closes it, so the open request keeps the Durable Object active. The Host therefore stops an idle container itself: after ten minutes with no Host RPC in flight, no `exec` in flight, and no turn lease open, an alarm closes the `Workspace` and destroys the container (ADR-0043). An idle stop loses what a platform restart loses: files the sync does not copy into the durable store, such as `node_modules`, `/tmp`, and paths outside `/workspace`. Every `exec` pulls its changes into the store before it settles. The container's idle CPU is the shim's disk walk, which polls every five seconds (ADR-0044).

## Artifacts (deferred)

Cloudflare Artifacts is a Git server per repository. The owner decided on 2026-10-02 to skip it for now. It does not fit the current stores: the workspace is a live POSIX working tree that a container needs, a container cannot mount the FUSE filesystem Artifacts' mount tool uses (ADR-0042), and module maps must load with no network call. One gap would fit it: cf-stumble keeps no copy of uncommitted work outside the workspace, so a reset or a project disconnect destroys it. A pilot could checkpoint that work to Artifacts before those two operations. A staging probe on 2026-11-08 showed the parts exist: Alchemy declares the binding (`Cloudflare.Artifacts.Namespace`) with the deploy token cf-stumble already uses, the Workspace Host's Git client pushes to and clones from an Artifacts remote with a token in the URL (push 0.3-0.7 s, clone and fetch 0.2-0.3 s), a read token's push gets 403, and `@cloudflare/computer` ships an `artifacts` command for its worker shell. Artifacts has no GitHub sync, and its operations are billed from 2026-11-12. Revisit it only after the owner approves that cost. Update 2026-11-09: the Supervisor now appends generation history (records and events, no module maps) to an Artifacts repository; see the overview.

## Deployment risk

Dynamic Workers and Durable Object facets are beta, and Computer is preview software. Paid-account tests must exercise the exact Worker Loader, facet, Computer, and workspace-capability path before the project treats the integration as deployable.
