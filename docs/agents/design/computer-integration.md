# Computer integration

cf-stumble uses Cloudflare Computer release 0.11.3: `@cloudflare/computer` from npm, source commit `9d11fa7b7f77cb8130d3f53f285ba8e0f8ea258b`, and image `ghcr.io/cloudflare/computer-computerd-linux-x64@sha256:2978fc5b5ad3b2bc8429ef83e2b56079f938003ca94c3c89612f78d509d027ff`. ADR-0026 records the decision. The workspace image builds `computerd` from that commit with `infra/workspace-image/computerd-walk.patch` applied. ADR-0042 records why the walk is patched.

The Workspace Host runs the container through `ContainerBackend`, with the container scheduled by the Host's Durable Object. The instance size is `WORKSPACE_CONTAINER_INSTANCE` in `infra/worker-settings.ts`, and the image is the `app` Container that `infra/alchemy.run.ts` attaches to the `WorkspaceHost` Durable Object class. Upgrade the package, the commit and the image together, and adopt a newer release only if the full application workflow passes against it.

The workspace image is built once in CI and published to GitHub Container Registry as `ghcr.io/sakompella/cf-stumble-workspace:<hash>`. The deploy and every machine that runs the container pull it, and nothing builds it locally.

The Workspace Host has two exec backends. The container handles Node, pnpm, TypeScript compilation, tests, and project commands. The container also runs every `git` command, with the image's real Git at `/usr/bin/git` (ADR-0052). The isolate backend runs just-bash in a Dynamic Worker over the SQLite workspace, so it handles text operations without waking the container; it has no Node, pnpm, `gh` or Git, and its only network use is `curl`. The shell module set ships the `@cloudflare/computer/shell/curl` group (`tools/build-shell-modules.mts`), and the shell's `ShellWorker` subclass routes its fetch through the `EGRESS` binding, an `IsolateEgressGateway` entrypoint the Host constructs from `ctx.exports` (`src/workspace/project/isolate-egress.ts`). The gateway forwards any method to any http(s) host and passes the request's headers and body through unchanged, and follows redirects itself (max 5). It reads the body once and sends it again on each hop, since the service binding delivers it as a stream that one fetch consumes. It follows `fetch`'s redirect rules: a 303, or a 301 or 302 after a POST, continues as a GET without the body and its `Content-*` headers, and any other redirect keeps the method and body. As `fetch` does, a redirect hop to another origin drops the caller's `Authorization` and `Cookie` headers for the rest of the chain. For api.github.com only, the gateway adds `Authorization: Bearer <token>` with the workspace's GitHub token, which it reads on the Host side from the `gh` hosts file (or the `GH_TOKEN` secret when the hosts file has none), and only when the request carries no Authorization header of its own; the token never reaches the isolate, is sent to no other origin, and a redirect hop off api.github.com drops it. The dynamic worker itself keeps `globalOutbound: null`; only the shell's fetch reaches the gateway. A command the isolate cannot run reruns in the container: an isolate exit of 127 or 129 before any stdout reruns the command there (`src/workspace/project/exec-fallback.ts`), and a kill during that switch starts no container, or kills the one already starting. A just-bash execution limit reruns there too, but only when the command has no write form: an exit of 126 whose stderr carries a limit message (iteration, recursion, output, command-count or any other `limit exceeded` wording), or an exit of 124 with an execution-deadline message, while a plain 126 such as permission denied stays an isolate result. A command has a write form when it redirects output (`>`, `>>`) or runs an isolate program in a form that writes files. `src/workspace/project/isolate-programs.ts` classifies every just-bash command, plus `cd`, `test` and `curl`, as running in the container, or in the isolate and never, always or sometimes writing; its type comes from the generated command list, so a just-bash upgrade that adds a command fails typecheck until the command is classified. `mktemp` runs in the container, because the path it prints is under `/tmp`, which a later container command could not find if the isolate had made it. The programs that always write are `cp`, `mv`, `rm`, `mkdir`, `touch`, `tee`, `chmod`, `ln`, `rmdir`, `split`, `gzip`, `gunzip` and `tar`. The sometimes-writing forms are `sed` with `-i`, `-f` or a `w` command, `yq -i`, `sort -o`, `awk` with `>` or `|` in its program, `curl -o`, `-O` or `-c`, and `xan split` or `xan partition` (`src/workspace/project/write-forms.ts`). The router tokenises the command to decide (`commandMayWrite` in `src/workspace/project/exec-routing.ts`). The isolate may already have run part of such a command before it hit the limit, so a rerun could append to a file twice or fail on a file the first run already moved. The image sets `init.defaultBranch` to `main` in Git's system configuration, so a `git init` in the container starts on `main` as the isolate's Git did. The same system configuration carries the fallback commit identity `cf-stumble <cf-stumble@users.noreply.github.com>`. Container Git pushes to GitHub with the credential helper that `gh auth setup-git` writes to `/workspace/.gitconfig`; the same credential install writes the owner's GitHub login there as the default commit identity (`user.name` the login, `user.email` `<login>@users.noreply.github.com`), so a commit in a fresh repository works without `-c` flags. A repository's own `user.name` and `user.email` win over both identities. The Workspace Host runs no Git: every clone, the harness's and each project's, runs in the container through one script (`reconcileClone` in `src/workspace/clone-script.ts`) with the image's real Git and the credential helper that `gh auth setup-git` wrote. A `bash` call that names no backend runs in the isolate when every program in it is one the isolate has and the command touches no absolute path outside `/workspace` (`/dev/null` is exempt: the isolate's shell serves it as a virtual device), and in the container otherwise. The router recognises such a path by its first directory, one of the image's root directories, `/nix` among them; a word such as the `sed` address `/foo/p` also starts with `/`, so a path under any other first directory counts as text. An `awk` program with a loop (`for`, `while` or `do`) always goes to the container, because one froze the isolate. A command whose isolate run ends without an exit code, or breaks, is run again in the container when it has no write form; when it has one, the harness returns the isolate's error with one line `rerun with backend: container`, so the model can rerun the command itself on the container backend. The router does not check whether just-bash prints the same text as GNU for a given form (`ls` with several paths, `cut -f`, `wc`, `echo -e`, `grep -r`, `2>&1`, globs with `?` or `[`); those forms run in the isolate, and a small difference in their output is accepted. The `bash` tool's optional `backend` parameter forces the container (`src/workspace/project/exec-selection.ts`). A forced `isolate` for a command that runs `git` is refused with an error that names the container, because the isolate has no Git; any other command the isolate cannot run goes to the container. The shell's modules ship as the static asset `ASSETS` and are loaded into the Dynamic Worker. The Host passes its workspace stub with each exec call (`src/workspace/project/isolate-shell.ts`). The shell must not open a new request back into the Host to get it: every exec of a turn runs inside the Host's `project()` call, each new request back into the Host counts toward the runtime's subrequest depth limit, and with such a request per exec every forced-isolate exec after the 13th in a turn failed with `Subrequest depth limit exceeded`.

Every clone sets `core.fileMode=false` (the clone script, `src/workspace/clone-script.ts`), as the Computer Git library did on the Host: the SQLite workspace cannot store the executable bit, so a mode-only change never shows in `status`. The cost is that a `chmod` shows in neither `git status` nor `git diff` in those repositories, which differs from real Git on Linux. A repository the agent creates with `git init` in the container gets whatever real Git finds when it probes the container's disk.
The event stream between the Worker and the harness carries all of a command's output. The harness keeps the tail it shows the model, and it writes the whole combined output to a file under `/workspace/.cf-stumble/tmp` (`pi-output-*.log`) once the output passes Pi's limit of 2,000 lines or 50 KiB. The bash tool reports that file as the spill path, and the model can read it to see what the tail left out. On each `project()` call the Host deletes all but the newest 50 of these files (`src/workspace/project/spill-retention.ts`). A project command asks Computer not to save its output (`output: false` in `src/workspace/project/computer-adapter.ts`), so the harness file is the only full copy and the terminal event carries only the exit code. The Workspace cap still bounds what the Host's own commands return: the last 2,000 lines or 64 KiB of each stream, whichever the output hits first (`WorkspaceOptions.output` in `src/workspace/workspace-platform.ts`, limits in `infra/worker-settings.ts`). When one of those streams passes the cap, Computer also saves it in full under `/workspace/.cf-stumble/output` and keeps the newest 50 files; nothing reads those files. Both directories sit outside `/workspace/projects` and `/workspace/harness`, so saved output never lands in a repository and old files cannot fill the disk.

## Workspace layout

One durable Computer workspace holds the owner's harness repository and the connected GitHub project repositories, each in its own directory with its own Git history. The page selects the project directory a turn starts in, but the shared filesystem is not a security boundary between the repositories.

Each project's conversations live in the serving facet's Pi Durable storage, outside the workspace and outside generation state (ADR-0048). Starting a fresh thread points the project at a new conversation without changing project files. The conversations and the workspace both survive generation changes.

The workspace name comes from the tenant and nothing else. The Worker reaches one Supervisor by a constant name, and the Supervisor derives its one workspace name from that, so harness builds and every project reach the same container.

`src/workspace-layout.ts` owns the layout:

| Path                               | Holds                                                                                   |
| ---------------------------------- | --------------------------------------------------------------------------------------- |
| `/workspace`                       | The workspace root. Every addressed path lives beneath it.                              |
| `/workspace/AGENTS.md`             | The managed instructions, above every repository.                                       |
| `/workspace/harness`               | The owner's editable harness checkout.                                                  |
| `/workspace/.config/gh`            | `gh` configuration, including the GitHub credential (`hosts.yml`).                      |
| `/workspace/.gitconfig`            | Git's global configuration: the `gh` credential helper and the default commit identity. |
| `/workspace/projects/<project id>` | One connected project's clone.                                                          |
| `/tmp/cf-stumble-builds/<commit>`  | Build scratch for one labeled commit, outside `/workspace`. It holds no repository.     |

The workspace behaves like an ordinary development machine: unrestricted outbound internet, `git`, `gh`, Node 22, python3 with venv, the Debian build tools (`build-essential`, `pkg-config`, `unzip`), and Nix with flakes in single-user mode. The image has no bun, Rust or Go; a repository with a `flake.nix` gets its toolchain from `nix develop`. The Nix store is `/nix` and `CARGO_TARGET_DIR` is `/tmp/cargo-target`, both container-local and outside the sync. An idle stop saves a container snapshot when the Nix store grew, and the next start restores it, so the next `nix develop` does not download its toolchain again (ADR-0053). GitHub credentials live in `gh` and Git configuration under `/workspace`, so they survive a container replacement.

cf-stumble owns `/workspace/AGENTS.md`. Whenever a run asks for a project capability, provisioning calls the Workspace Host's `ensureManagedInstructions`, which writes the current text over whatever file is there. An instruction change reaches the workspace at the first run after a deploy, and an edit to the file lasts only until the next run. The Host refuses the write when the workspace root or the file is a symbolic link, or the path is a directory. Provisioning never writes a repository's own `AGENTS.md`.

### Resets and fresh threads

A workspace reset would delete files under a running command, so the Supervisor refuses it with HTTP 409 `run-active` while a run is active, and a project disconnect the same way when that project's own run is active. A run in another project does not block a disconnect: the disconnect removes only that project's clone, and a run works in its own project's clone. A run that reads another project's clone on purpose (ADR-0038 allows it) can lose it, as on any development machine. A run is active from when the facet reports its conversation running until the facet reports it settled, or until its own deadline passes. The facet reports each running conversation with its run, the first input submission Pi placed for it, so a queued follow-up that starts in the same commit as the previous run ends is a new run: the Supervisor ends the previous run's workspace capability and gives the follow-up its own deadline. A fresh thread is allowed during a run: it aborts the project's current conversation and points the project at a new one. Submitting a message, opening a conversation, starting a fresh thread, and a disconnect that releases the pointer each run one at a time per project (`ProjectThreads`, in memory), and each re-reads the project inside that turn, so a message checked before a disconnect never gives the disconnected project a new conversation. The Host also refuses a reset with HTTP 409 `workspace-busy` while it runs a build, provision, removal, managed-instructions write, or credential install.

From the moment a reset reaches the Supervisor until the Host answers, the Supervisor refuses a new message, a connect or disconnect, a project capability, and a second reset with `workspace-busy`. The Host applies the same exclusion for the same span: its operations refuse without running (a file change answers `workspace-busy`, a credential install `workspace-unavailable`), a project capability request throws, and a second reset answers `workspace-busy`. Both exclusions live in memory, one per object instance.

A reset and a disconnect destroy work on purpose; the owner commits and pushes what matters first. A reset deletes the Workspace Host's whole storage and destroys the container: the harness checkout and every project clone with their uncommitted changes, unpushed commits, local branches and stashes, the managed instructions, the `gh` credential and `/workspace/.gitconfig`, saved command output, every container process and container-local path (`/tmp`, `node_modules`, `/nix`), and the container snapshot, so the next container starts from the image. It keeps the Supervisor's state: the project list, each project's conversation, the generations and their module maps, and the ChatGPT login. The next run clones each repository again from GitHub and reinstalls `GH_TOKEN` when it is set; a device-flow login needs a new authorization. A disconnect removes only that project's clone, its catalog entry and its conversation pointer. Pushed work comes back with `git fetch origin <branch>` and `git checkout -b <branch> FETCH_HEAD` in the new clone; a staging check on 2026-11-14 restored a pushed commit that way after a reset, while the unpushed commit and the untracked file were gone.

### Turn capability

A project's conversation runs in that project's directory. The project capability addresses the whole workspace, so the agent can read a sibling repository or the managed instructions, and the path guard is the workspace root, read from `WORKSPACE_ROOT` in `src/workspace-layout.ts` by both the guard and the path translation.

A run asks the Supervisor for a capability through its host's `workspace`, naming its conversation, and the capability lasts only as long as that run. The Supervisor refuses a conversation whose run it has no record of or whose deadline has passed. The Supervisor asks the Host for it with the run's remaining time before its deadline. The Host turns that into one end time for the lease and the capability: its calls are refused from then on, its commands end at it, and its lease expires then. The Supervisor ends the capability when the run settles. After that, `lstat`, `readFile`, `writeFile`, and `startExec` answer `turn-ended`, also through a duplicate the generation kept, so a generation that ignores the end of its run cannot keep editing the workspace while a later run works. A refused call does not count as workspace activity, so late calls cannot keep the idle container running. `kill` and `endTurn` still answer. A container replacement refuses only the next command of a live run, with `container-restarted`, and file calls go on because the files are durable (`src/workspace/project/target.ts`). The capability owns that acknowledgment: when the command that connects to the new container is the one that reports `container-restarted`, the capability counts that as the refusal and the next command runs.

When a tool call is aborted, the env kills its running commands and only then disposes the capability (`src/facet/generation-1/computer-env.ts`). The env counts a command as running from the moment it calls `startExec`, not from the answer that carries the operation id, and the kill waits for each start to answer (`killAll` in `src/facet/generation-1/execution-env-exec.ts`). Before 2026-11-18 an abort that arrived while `startExec` was still in flight, about 110 ms after the model call ended, found no operation id, so the env disposed the capability and the command's later kill reached a disposed stub: the e2e cancel step then ran its `sleep 300` to the end four times. With the fix, 97 cancel runs on a staging stage, 11 of them inside that window, all settled within 2.9 s.

The generation's `ExecutionEnv` (`src/facet/generation-1/execution-env.ts`) calls only this capability. It implements only the members that the installed tools (Pi Durable 1.5.0's coding tools) and the prompt call. Every other member answers a `not_supported` `FileError`, and the optional `listFiles` is left out. The capability has no open file handle, so a binary reader reads the whole file into memory when it opens, which limits it to `MAX_FILE_BYTES`.

When you bump Pi Durable, search the new version for calls to the members that file stubs out before you deploy, and implement any member it now calls:

```sh
cd node_modules/@earendil-works/pi-durable/dist && rg -n -g '*.js' -g '!storage/jsonl' -g '!testing' \
  '\.(readBinaryFile|appendFile|openTextLineReader|readTextLines|truncateFile|flushFile|renameFile|listDir|openDirReader|watch|createDir|remove)\('
```

In 1.5.0 it finds only Pi's own Node environment calling itself (`env/node.js`), a doc comment in `harness/transcript.js`, and two unrelated `watch` methods in `harness/harness.js` (the host's views and the task graph).

A generation must also speak the Supervisor's current facet-to-Supervisor protocol. `FACET_COMPATIBILITY` in `src/facet/runtime-contract.ts` is `pi-durable@<version>/host-<N>`, the facet reports it from `compatibility()`, and the startup check, activation and rollback compare it exactly. Bump `host-N` when the facet-to-Supervisor RPC contract changes: a host call the facet makes (`arm`, `running`, `workspace`) or a facet method the Supervisor calls (`host-6` moved the model capability from the Loader `env` into `attach`). A Pi Durable bump changes the key by itself. An optional trailing argument, such as the `failed` map that `running` carries, leaves the key alone: an older facet omits it and an older Supervisor ignores it.

## Harness execution

The harness source is TypeScript, while Dynamic Workers need Worker-executable modules. Computer builds a canonical module map for a labeled harness commit. The Supervisor validates it and stores it in R2 under that commit, so nothing rebuilds to serve or roll back. A module map is named Worker modules plus the entry module's name; a single-file bundle is a one-module map, not a second shape. The Supervisor names the Worker Loader entry by the commit ID (ADR-0027). Loader entries are cached with their `env`, so that `env` is empty, and the serving instance's model capability is an argument of the facet's `attach`.

### Build isolation

A build extracts its commit into `/tmp/cf-stumble-builds/<commit>` and clears that directory first. The path is container-local, outside `/workspace`, and holds no checkout, so clearing it destroys nothing. A build script receives every path, ref and URL as a quoted variable assigned once at its top (`name=<quoted value>`, then `"$name"`), and the shell tests run every script under a root whose name has spaces and glob characters. The harness directory is the owner's editable clone. The build's provision step is one container script and the Host runs no Git for it (`src/workspace/harness-provision.ts`; until 2026-11-16 the Host cloned a missing harness with Computer's Git client, and until 2026-11-14 it also read Git objects: Computer's `git.show` and `git.configGet` loaded pack indexes and read packs out of SQLite on every provision). The script first reconciles the clone with the same script as a project's: it takes a lock, clones the harness at depth 50 without blobs through a staging directory when it is missing, after the size check of `docs/agents/design/github-connection.md`, and refuses rather than deletes a populated directory that is not a repository. It then checks that the origin is the harness remote (a checkout whose origin is another remote is refused) and handles the working tree and any further history. A pinned commit the checkout lacks (`git cat-file -e <commit>^{commit}` fails) is fetched there by its ID (`git fetch --depth=50 origin <commit>`, which GitHub serves for any commit a ref reaches, also an unmerged branch's), and otherwise the step fails with `harness commit <commit> is not in <remote>` and Git's reason. Then the container fetches the checkout's branch and advances the checkout: one with local tracked changes stays as it is, with a message; one that contains its upstream (the usual case, and the case after a self-modification commit) stays as it is; one that its upstream contains is fast-forwarded, however far behind it is; a detached or diverged checkout stays as it is with the message `cannot fast-forward`. `git merge-base --is-ancestor` decides containment; when neither direction holds on the shallow clone, the container fetches the full history once (`--unshallow`) and decides again. Before 2026-11-14 the Host also ran Computer's `status`, `merge` and `checkout`, and deepened the fetch (500, 5,000, then 100,000 commits), on its own thread. That work runs synchronously against the SQLite store: after container Git had rewritten the index, one `status` of the harness cost the Host 8 to 18 s of CPU, and on 2026-11-13 a self-modification's provision ran 30 s and the platform reset the Host (`Durable Object storage operation exceeded timeout which caused object to be reset`). One provision runs at a time per Host (a semaphore in `ComputerWorkspaceOperations`). The later `checkout` step only reads the repository with `git archive` in the container. `HarnessArtifacts` (`src/supervisor/artifacts/index.ts`) admits one build per commit at a time, and a second request for a commit already building joins that build, because two builds of one commit would clear each other's directory.

### Build phases

The Supervisor's build runs `HARNESS_BUILD_CONFIGURATION.buildPhases` (`src/harness-build.ts`) in a directory `git archive` just wrote, which has tracked files only: a production install (`--prod`) from `pnpm-lock.yaml`, then a build of the module map. The build needs only the runtime packages and `esbuild`, which is a production dependency for that reason, and Node runs the build script with its own type stripping. Each phase is its own Durable Object RPC with its own exit code, output capped by the Workspace's output limits, and `WORKSPACE_COMMAND_TIMEOUT_MS` timeout, because one long command died three times with no sign of which phase had been running. The publish step copies the module map to a file of its commit's own (`/workspace/.cf-stumble-build-output/<commit>.json`), so two commits published at once never read each other's map, and a discard removes only that file.

A fresh build container needs pnpm, which downloads the version `package.json` pins on first run; Node 22; `registry.npmjs.org`; and `git` and `tar` for the archive. The Host's Git client reaches `github.com` over HTTPS for the clone and fetch. A developer machine hides most of these.

The release proof is two clean Computer builds of one labeled commit.

## Paid probes

Probes that run on the disposable paid Cloudflare account are approved. A local container run proves tool availability and build behavior, not deployed-platform behavior, and a report must not claim otherwise. A probe that cannot run states the blocker instead of reporting a simulated result as real.

## Container lifetime

The container does not stop by itself while the Workspace Host exists. Computer's backend accepts the WebSocket that computerd opens back to the Host, and nothing closes it, so the open request keeps the Durable Object active. The Host therefore stops an idle container itself: after ten minutes with no Host RPC in flight, no `exec` in flight, and no turn lease open, an alarm closes the `Workspace` and destroys the container (ADR-0043). An idle stop loses what a platform restart loses: files the sync does not copy into the durable store, such as `node_modules`, `/tmp`, and paths outside `/workspace`. When `/nix/store` grew since the last snapshot of the current image, the Host saves a container snapshot before the destroy, and the next start restores it with `/workspace` emptied first, so paths outside `/workspace` come back from the snapshot and `/workspace` comes only from the store (ADR-0053). Every `exec` pulls its changes into the store before it settles. The container's idle CPU is the shim's disk walk, which polls every five seconds (ADR-0042). A Host restart forgets when the workspace was last used, because the Host keeps that time in memory: a new instance counts itself idle for one limit, so the next alarm that wakes it stops the container at once, even when that alarm was set to check idleness shortly after the last command. After a restart on 2026-11-14 the container stopped 48 seconds after its last command, before a background job wrote its file; the files written until the stop were in the store, and the job was gone. The sync of many files is slow: after a command wrote 20,000 small files in 1.2 seconds, its post-command sync took 285 seconds, and while those files stayed in `/workspace` the first container command of a run waited about four minutes before it ran, and a later one in the same run about 30 seconds.

## Artifacts (deferred)

Cloudflare Artifacts is a Git server per repository. The owner decided on 2026-10-02 to skip it for now. It does not fit the current stores: the workspace is a live POSIX working tree that a container needs, a container cannot mount the FUSE filesystem Artifacts' mount tool uses (ADR-0042), and module maps must load with no network call. One gap would fit it: cf-stumble keeps no copy of uncommitted work outside the workspace, so a reset or a project disconnect destroys it. A pilot could checkpoint that work to Artifacts before those two operations. A staging probe on 2026-11-08 showed the parts exist: Alchemy declares the binding (`Cloudflare.Artifacts.Namespace`) with the deploy token cf-stumble already uses, the Workspace Host's Git client pushes to and clones from an Artifacts remote with a token in the URL (push 0.3-0.7 s, clone and fetch 0.2-0.3 s), a read token's push gets 403, and `@cloudflare/computer` ships an `artifacts` command for its worker shell. Artifacts has no GitHub sync, and its operations are billed from 2026-11-12. Revisit it only after the owner approves that cost. Update 2026-11-09: Aditya chose R2 over Artifacts for generation history, so the Supervisor writes the history (records and events, no module maps) to the `MODULE_MAPS` bucket (`dc03a4a2`); see the overview.

## Deployment risk

Dynamic Workers and Durable Object facets are beta, and Computer is preview software. Paid-account tests must exercise the exact Worker Loader, facet, Computer, and workspace-capability path before the project treats the integration as deployable.
