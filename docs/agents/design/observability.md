# Operational log

cf-stumble writes a few structured events: one per run start and end, one per model call, one per idle stop, one per container
start and reset, and the ChatGPT and GitHub credential faults. Each event is one plain object passed
to one `console` call, so Workers Logs indexes every field and a query filters on `event` or
`outcome` instead of matching text. The Supervisor and the Workspace Host run in the `cf-stumble`
Worker, so their events are in its logs. Everything else is in the platform's invocation records,
Workers traces, and Issues.

## Writing an event

`src/diagnostics.ts` owns the logger:

- `logEvent(level, event, fields)` writes `{ event, level, ts, ...fields }`. `info` goes to
  `console.log`, `warn` to `console.warn`, and `error` to `console.error`. A field value is a
  string, a number, a boolean, or `null`. Every string field is redacted with `redactCredentials`
  and a JWT pattern, then cut to 200 characters.
- `logRedactedCause(context, cause, knownToken?)` writes the redacted text of a thrown cause, cut
  to 400 characters. A catch block that may see a secret in the cause uses it.

The redaction covers recognized patterns, not all secrets. A caller passes ids, codes, counts, and
durations, never a message, an event's text, file contents, command text or output, a header, a
cookie, a token, a device or user code, or a GitHub login.

Use `info` for the ordinary lifecycle, `warn` for a degraded path the system survived, and `error`
for a fault it caused or could not recover from. Add an event only when an operator could not answer
the question from the platform's records; name it `area.thing` and add it to the table below.

## Querying

Stream live events with Alchemy:

```sh
pnpm alchemy logs --config infra/alchemy.run.ts --stage prod --tail
```

For past events, open the Cloudflare dashboard, Workers & Pages, `cf-stumble`, Observability, and
filter on `event` (for example `event = run.settled`). Workers Logs keeps events for 7 days.

Cloudflare Issues and Workers traces are on (`observability.issues` and `observability.traces` in
`infra/worker-settings.ts`; traces only on the stage `prod`); a deployment from a configuration without
`issues` turns Issues off. Issues groups uncaught exceptions, failed invocations, 5xx responses, and
`console.error` output, so an `error` event appears there; it ignores `warn`, and it misses work
that is slow or expensive but succeeds. Every sampling rate is 1. A span is one event in the logs
quota (20 million a month on Workers Paid, then $0.60 per million); one cold start of the workspace
wrote about 12,600 spans. If the bill grows, lower `traces.headSamplingRate` first.

## Checking a running deployment

Run `pnpm ops:check` after a staging deploy or an e2e run, and when the bill looks wrong. It needs a
live account, so it is not part of `pnpm verify`. The workflow `.github/workflows/ops-check.yml` also
runs it on production once a day (13:41 UTC) over the last 26 hours, so consecutive runs overlap and
a late start leaves no gap. A failed run means a finding or an `unknown`: read the `✗` lines in the
run log. GitHub reports the failure through its Actions notifications. It checks three things: a workspace container that
kept running past the Host's idle stop (rule `ran-past-idle`), `facet.session-failed` events in
the window (rule `facet.session-failed`), and a Durable Object that still runs an older Worker
version after the latest deployment (rule `do-version-skew`). It prints one check mark when all is well and one line per
finding otherwise, and exits 1 on any finding or `unknown`. After that it prints an informational
line, `i model cache hit rate`, with the sum of `cachedTokens` over the sum of `promptTokens` of the
`model.call` events in the window. The line never changes the exit code. It is fetched apart from the
checks, so a failed fetch drops the line only. When telemetry returns a full page (2000 rows), the line
says the rate is a sample. A second informational line, `i git commands`, counts the `exec.finished` events whose
`program` is git: the share that ran in the isolate, the subcommands per backend, and the subcommands that fell back
from the isolate or that the isolate refused. It is fetched and reported the
same way. A third informational line, `i generations`, reads the R2 generation history (see the overview) through the
R2 REST API: it finds the Worker's `MODULE_MAPS` bucket in the Worker's settings, lists `history/events/`, and reads the
activation or rollback with the highest epoch and the events written in the window. It prints the generation that event
made active and its actor, the window's activations by actor (`owner`, `conversation`, and `unknown` for events written
before actors existed), and its `proven` and `rolled-back` counts. A missed history write leaves this line behind the
Supervisor, so `stumble gen status` stays the authority for the active generation. When a call fails, the line says
`i generations unknown:` with the reason; it never changes the exit code.

**Sources.** For the window (`--since 90m|2h|1d`, ending now), it reads:

- Workers Logs (`workers/observability/telemetry/query`): every fetch invocation of the Worker, with
  its end time, `$workers.wallTimeMs`, and URL, from the first metrics bucket of the window back
  through one run deadline plus the idle limit. Only owner API routes that can reach the workspace
  count as work. The same query set also reads the `run.started` and `run.settled` events of
  conversation runs, so a queued run counts from when it actually ran, not from when its message
  was admitted; a failed or row-limited run query makes the whole check `unknown`. `src/routes/route-pattern.ts` lists
  each route as `record-only` (status, project list, GitHub and ChatGPT connection, the backend
  setting (a change stops the container and never keeps it awake), and a
  project's events, abort and fresh thread: the Supervisor and the facet answer without the
  workspace; the page keeps an events stream open) or `workspace` (messages, disconnect, connect,
  GitHub refresh and authorization, generation submit, activate and rollback, workspace reset). The page and Durable Object fetches never reach the
  workspace.
- GraphQL `containersUsageAdaptiveGroups`: `allocatedMemory` byte-seconds per five-minute bucket,
  divided by the instance's memory (`WORKSPACE_CONTAINER_MEMORY_MIB`) and by 60, gives
  running minutes. A bucket counts at most five minutes.

**Rule `ran-past-idle`.** Each `workspace` request allows the container to run from its start until
its end plus the idle limit (`WORKSPACE_IDLE_STOP_MS`). A conversation run allows its own lifetime:
a `run.settled` event covers from its settle time back by its `totalMs`, a `run.started` event
without one covers the run deadline (`PROJECT_RUN_DEADLINE_MS`), and the idle limit follows each.
A run of consecutive running buckets that exceeds that allowance by more than 10 minutes is a
finding. Only whole five-minute buckets inside the requested window count, and buckets newer
than 10 minutes are still filling and do not count. The check mark names the window up to the last
complete bucket, not up to now, and a window with nothing complete prints `unknown`. The finding lists the routes and end times of
the last three requests before the run ended, which shows what kept the container awake.

**Rule `do-version-skew`.** A Durable Object adopts a new Worker version when it restarts, and an
active one can run older code for a while (`docs/deploy.md`, "Durable Objects and new versions").
The check reads the latest deployment from `workers/scripts/<worker>/deployments` and then asks
Workers Logs, for each class (`Supervisor`, `WorkspaceHost`), for invocations whose
`$workers.scriptVersion.id` differs from every deployed version, from five minutes after the
deployment (`DO_UPDATE_GRACE_MS`, the default code update delay) to now. Every `do.started` event
and every other invocation carries that field, so a Durable Object that serves a request on old
code shows up even if its constructor ran long before. The query returns only the old-version
calls, so the 2,000-row limit is reached only when the skew itself is large; the check then prints
`unknown`. A class that no one called since the deployment is silent and passes: an instance that
runs no code cannot run the wrong code, and its next request starts it on the new version. The
check ignores `--since` because the deployment, not the window, bounds it. It is independent of
the container checks: a failed deployments call prints `unknown` and leaves the other rules
alone.

**Limits.** Other work that holds the container after its request ended is covered only by the 10-minute slack. A stuck container shows up about 30
minutes after the last request with the defaults, or about 40 after a message.

**Credentials.** `CLOUDFLARE_API_TOKEN`, else the `cf` login JSON
(`~/.config/cloudflare/config/default.json`, after `pnpm exec cf auth whoami` refreshed it). GraphQL
needs Account Analytics Read, and the `i generations` line needs Workers R2 Storage Read; an API token with both is better for repeated runs. The account is
`CLOUDFLARE_ACCOUNT_ID`, then the only account the token sees. The token goes in
the `Authorization` header only and is never printed. Use `--worker <name>` for another Worker.

**Unknown.** Missing data never reads as fine. A request to an `/api/` route that
`route-pattern.ts` does not list counts as record-only, since the router answers it 404 without the
Supervisor; a workspace route left out of the table therefore shows up as `ran-past-idle`. A
missing token or account, a failed call, a missing application, an unexpected response, or a query
that hit its row limit (2,000 requests or 5,000 usage rows) prints one `unknown` line with the
reason. Use a shorter `--since` after a row limit.

The queries are in `tools/ops-check/fetch.mts`. To check whether a stop happened without the
metrics lag, `GET /accounts/<account-id>/containers/applications/<container-app-id>/instances`
lists instances with `status.state` (`running` or `inactive`); the applications list gives the id.
Billing data needs an API token with Billing Read; the `cf` login cannot get that scope.

## Noise from the container

Container output does not pass through the Worker's redaction. Base64 dumps of source text appeared
in the container logs from 2026-09-24 to 2026-09-28, from an unknown source, and none since. If they
come back, find the container log line, then read the upstream code at `COMPUTER_COMMIT`.
