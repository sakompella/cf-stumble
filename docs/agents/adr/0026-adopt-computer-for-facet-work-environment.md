# The facet uses a pinned Computer workspace on the Worker-shell backend

The facet's agent workspace uses an exactly pinned `@cloudflare/computer@0.2.1` release for its durable filesystem, ordinary Git workflow, and runtime. A package update must be an explicit version change, never a semver range that moves on its own. This remains facet-owned mutable state under ADR-0024: Computer does not threaten recovery unless a binding exposes supervisor recovery authority.

Start on Computer's Worker-shell backend. It supplies just-bash over a virtual filesystem and roughly 77 core utilities, but no OS processes, compiler, or `npm install`. The near-term facet loop only edits its harness and submits a candidate; Worker Loader accepts the JavaScript it emits. The supervisor, not the facet, validates the candidate by replaying it against the compatibility corpus, so the facet needs no test runner to prove its own work and a self-run result would not be gate evidence. Worker-shell is sufficient for that loop while adding no container awake charge, image or credential surface, or cold start.

Move to the container backend when the facet needs to run a compiler, install packages, or execute a real test runner in its own agent workspace. That is a judgement about what the harness has grown into, not a milestone. The container backend is a Linux process environment running `computerd`, at roughly $0.129 per hour for standard-2 while awake, a 1–3 second cold start, and a larger credential and image surface. As checked for this decision, [#114](https://github.com/cloudflare/computer/issues/114) remains open and reports that deployed container WebSocket upgrades never complete, which supports deferring that dependency. Switching backends does not change the Computer API the facet codes against, so starting narrow does not constrain that later move.

The facet authors and emits plain JavaScript. Worker Loader receives JavaScript regardless of backend, and Worker-shell has no compiler. `loadAgent` (`src/agent/loader.ts:88`) currently passes only an `agent.js` module even though Worker Loader accepts a module map and a stored generation can contain many modules, so multi-module or vendored output needs a small change there. A compiler in the agent workspace after a backend change would be a self-check that improves candidate quality, not gate evidence: the supervisor still validates the candidate by running it, and a facet can fake its self-check only by submitting a candidate that fails replay. Revisit the authoring language with the backend if the facet moves to the container backend, where TypeScript becomes possible.

Candidate submission remains open: we have not designed a sanctioned path that hands the supervisor immutable candidate material without giving the facet a write path into supervisor recovery records.
