# Run every git command in the container's real Git

> **Review:** Human-approved

Every `git` command the agent runs goes to the workspace container and runs the image's real Git at `/usr/bin/git`. The isolate has no Git, and the Workspace Host runs none either: a project's clone and the harness's clone run in the container through `reconcileClone` (`src/workspace/clone-script.ts`), and the harness provision is one container script (`src/workspace/harness-provision.ts`: clone reconcile, a check that the commit is present, fetches and a fast-forward).

**The alternative was Git in the isolate.** A CLI layer over Computer's Git library (isomorphic-git) made the isolate the only writer of `.git`, and the container's `git` was a read-only wrapper that forwarded every write to the Workspace Host. That layer reimplemented Git's output and rules, about 4,800 lines with 3,600 lines of tests, and it still did not cover `diff`, `show` or `log --stat`. On 267 recorded scenarios, an agent would have been misled in 23 cases by the layer and in 70 by Computer's Git without the layer; 14 of those 70 left the repository in a different state than Git would, for example an empty commit or a deleted checked-out branch. No wasm Git could replace the layer: none prints Git's command-line output, gitoxide has no push, and a Rust port was estimated at 21 to 27 days. Real Git in the container has none of these differences.

The Host's own clones moved to the container as well. Computer's Git client ran isomorphic-git on the Host's own thread, and that work once ran long enough that the platform reset the Host. It also counted only packed kilobytes, which let a small pack of many small files past the 3,000-blob limit. One container script applies one size policy (`docs/agents/design/github-connection.md`) to every clone.

**The cost is the container.** A Git read takes about 330 ms in a warm container instead of about 80 ms in the isolate, and a Git command on a stopped container starts it (about 6 s) and keeps it running until the ten-minute idle stop (ADR-0043). A week of production telemetry named no Git command, and about half of all commands already ran in the container, so the extra container time is small. On a provider machine (ADR-0050), Git needs the provider's container, as every other command that is not an isolate program already does.

Connecting a project starts the container too, and so does every run in the harness project: `WorkspaceReadiness.obtain` provisions the harness workspace before it hands out the run's capability, so on a stopped container the run waits about 6 s before the first model call, and the page shows only `running` meanwhile. A connected repository's provision reads the store and starts no container once its clone exists, so there the first command that needs the container pays the start.

The router refuses a `bash` call that forces `backend: "isolate"` for a command that runs `git`, with an error that names the container. Other commands the isolate cannot run still go to the container. Git is refused instead, because a caller that forces the isolate for Git expects the isolate's old Git, and the error tells it where Git runs now. Container Git pushes with the credential helper that `gh auth setup-git` writes when a GitHub credential is installed.
