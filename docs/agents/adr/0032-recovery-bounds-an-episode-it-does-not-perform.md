# Bound a recovery episode the Supervisor does not itself perform

> **Review:** Agent-only

A failure event opens one recovery episode, deduplicated by the failure event's own identifier so the same failure arriving twice does not start a second episode. The episode snapshots its policy, so a later policy change cannot rewrite the bounds an episode already running is held to.

The episode first picks a fallback: the most recently labeled generation, other than the one that failed, whose retained evidence qualifies it under ADR-0031. When no generation qualifies, the episode is blocked and says so, and nothing is routed anywhere. Falling back to Generation 0 because it happens to exist, or to a null-like sentinel, would route traffic to code no evidence supports.

The Supervisor bounds repair and startup checking rather than performing either. ADR-0024 keeps mutable harness code in the facet and the recovery harness immutable, and materialising a repaired generation needs a model call this project cannot make yet. A repair attempt is a keyed operation the Supervisor opens, bounds and records. A reported repair success names a harness commit, then opens a separate startup-check operation for the same attempt. The external caller submits that commit as a generation and runs the ordinary startup request from ADR-0029; recovery does not run model work or await that request inside a SQLite transaction.

The Supervisor accepts a reported startup pass only when the named generation has the repaired commit, is ready, and has a latest passing preparation check recorded after the startup-check operation opened. It snapshots the greatest preparation-check ID when it opens the operation, then stores the verified commit, generation label, and check ID in the completed report. Recovery never activates the checked generation; activation remains a separate, epoch-checked control request under ADR-0033.

Each operation key names the episode, kind, and repair attempt, so a crash reuses the original key instead of issuing another effect. An operation past its deadline needs reconciliation and keeps that key. Reconciliation may settle an operation after the episode budget expires, but cannot open another operation; the next resume records budget exhaustion. Exhausting repair attempts also completes the episode with its fallback retained.

Every episode leaves a durable recovery report carrying the failure event, failed generation, fallback, snapshotted policy, attempts used, phase, result, errors, and any verified candidate. The current SQLite table uses direct `CREATE TABLE` constraints because it has not been deployed. A deployed version would need a rebuild-and-copy migration, because `ALTER` cannot widen the phase constraint.

Two clocks stay separate. The epoch versions generation-control state for ADR-0033's staleness check: generation table changes, active-label changes, and preparation-check changes. Each committed change advances the epoch once. Observations and recovery records do not move it because activation and rollback do not read them as decision inputs. The activation identifier moves only when a generation becomes active. While one counter served both, labeling an unrelated commit ended the running generation's evidence era and discarded its accumulated credit; a regression test now pins that.

An evidence era is still keyed by the activation identifier _and_ the latest passing preparation check, and that second key has the same shape of problem. A redundant passing check on an already-ready generation records a new check and so starts a fresh era, zeroing the credit the generation had earned. That is deliberate today, because a failure observation is only cleared by a fresh check, but it means a diagnostic re-check silently discards evidence, and a re-check exercises a candidate facet rather than the one serving traffic. Whether re-admission should require re-activation instead is an open question, not a settled decision.

Time is a parameter throughout, because Workers pins `Date.now()` across a handler's I/O interval and a test cannot advance time by waiting. Nothing here is scheduled: no Durable Object alarm resumes an episode, because alarm survival across hibernation needs paid-runtime evidence this project does not have.
