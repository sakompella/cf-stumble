## Acceptance criteria and evidence

1. **Production request bodies and RPC types carry principal plus command only; `journal.ts` is
   deleted; a fresh-schema test proves the table is absent; no retained local journal table.**
   - `GenerationRequest` (`src/supervisor/control/request.ts`) is `{ principal, command }`, no
     `requestId`, no fingerprint field.
   - `src/routes/generations.ts` request bodies (`GenerationControlBody`,
     `GenerationSubmissionBody`) carry no `requestId`; `hasExactKeys` rejects one if present
     (`test/routes/generation-requests.test.ts` and `generation-submission.test.ts`, the "a
     request ID" malformed-body cases).
   - `src/supervisor/control/journal.ts` is deleted (`git show --stat` above).
   - `test/supervisor/control/schema.test.ts` queries `sqlite_schema` on a fresh Supervisor and
     asserts no table named `generation_control_journal` exists.
   - No compatibility/cleanup journal was introduced; there was nothing to migrate because the
     journal table lived only in Durable Object SQLite behind the deleted code path, and no
     production system reads it directly.

2. **Candidate resubmission returns the existing label; activation of the active label with the
   current epoch is a no-op; activation/rollback with a stale epoch reject; rollback still
   requires a ready label that ran before.**
   - `Generations.labelInTransaction` (unchanged, pre-existing) returns the existing generation for
     an already-labeled commit; `GenerationControl.submit` calls it directly with no journal
     layer in between. Proven at three levels:
     `test/supervisor/control/control.test.ts` → "resubmitting the same harness commit returns
     the existing generation" and "...after Durable Object eviction"; `test/routes/generation-submission.test.ts`
     → "resubmitting the same harness commit returns the existing generation, not a new label";
     `test/routes/generation-candidates.test.ts` → "resubmitting the same passing commit..." and
     "...an unbuildable commit...".
   - `Generations.activateInTransaction`/`decideActivation` (unchanged, pre-existing) already
     returns `effect: "no-op"` when the target label is already active; `GenerationControl.activate`
     no longer lets a journal short-circuit this. Proven in
     `test/supervisor/control/control.test.ts` → "activating the active generation with its
     current epoch is a no-op, but a stale epoch rejects"; `test/supervisor/rpc-surface.test.ts` →
     the epoch-checked-activation test; `test/routes/generation-control.test.ts` → "activating the
     already-active generation with the current epoch is a no-op".
   - Stale-epoch rejection: same tests above also send a repeated/older epoch and assert
     `{ ok: false, problem: { code: "stale-epoch" } }`.
   - Rollback-requires-previously-active-ready is unchanged production logic
     (`GenerationControl.rollback`); regression-tested in `control.test.ts` → "rollback requires
     a target generation that has been active before".

3. **Generation rows, active selection, and preparation checks advance the epoch under existing
   rules; relay observations and recovery records do not; failed candidates leave active traffic
   unchanged.** No change was made to `Generations`, `decisions.ts`, relay, or recovery code (out
   of this task's listed scope); this behavior was already correct and is exercised unchanged by
   `test/supervisor/epoch-scope.test.ts` and `test/supervisor/evidence-era.test.ts`, both of which
   still pass with the `requestId` field removed from their request literals.

4. **Duplicate candidate requests do not replay an old response; preparation is not silently
   rerun as a substitute for journaling; direct-command semantics preserved without automatic
   retries.**
   - There is no journal, so nothing "replays" a stored response; every request is decided fresh
     against current state.
   - `handleGenerationSubmission` still runs `prepareGeneration` once per request as an explicit,
     already-tested operation (`decidePreparationCheck` in `src/supervisor/generations/decisions.ts`,
     unchanged and out of this task's scope): a repeated check that agrees with the recorded
     outcome records `effect: "no-op"` rather than duplicating it, and a check that disagrees is
     refused as `contradicts-recorded-outcome`. This existing, tested behavior is what "not
     silently rerun" cashes out to given `journal.ts`, `routes/generations.ts`, and
     `supervisor/control/` are this task's listed scope. `test/routes/generation-candidates.test.ts`
     → "resubmitting the same passing commit returns the existing generation without labeling it
     twice" asserts the second preparation report has `effect: "no-op"`, not `"recorded"`.
   - No automatic retry loop was added anywhere in the route or control layer.

5. **After uncertain transport failure, the page reads current status before another
   activation/rollback; request-ID controls and obsolete tests/deployment examples removed;
   tests exercise repeated delivery with current state, not exact replay.**
   - `src/page/script-generations.ts`'s `runControl` already reads `observedEpoch()` from the
     rendered status section before every activate/rollback call (unchanged control flow); the
     comment above it now states the uncertain-transport-failure policy explicitly.
   - All request-ID inputs, displayed fields, and the `newRequestId()` helper are removed from the
     owner page (`script-generations.ts`, `markup.ts`, `element-ids.ts`, `script-helpers.ts`).
   - `scripts/deploy/README.md`'s Generation 0 curl examples no longer send a `requestId`.
   - Every rewritten test exercises repeated delivery against current server state (resubmission,
     no-op activation, stale epoch) rather than asserting an exact replayed value.
