## Which vendored Pi streaming helper was used, and why not the other two

Per the brief, all three of `vendor/pi-v0.84.4/index.ts`'s streaming exports were evaluated before
writing anything:

- **`createAssistantMessageEventStream`** — used, unchanged. It already was the target type;
  nothing about incremental delivery required a different container, only pushing more than one
  event into it.
- **`createGatewayBindingFetch`** — not used. It translates HTTPS-shaped requests into
  `env.AI.gateway(id).run(...)` binding calls, i.e. it requires an AI Gateway resource. `wrangler.jsonc`
  only configures a plain `ai` binding (`{ "ai": { "binding": "AI" } }`); no AI Gateway exists in this
  repo. Provisioning one is an infra/dashboard change outside this task's listed scope and outside
  tonight's no-paid-spend constraint, and it would also route the call through the heavier
  `openai-completions` HTTP pipeline below for no benefit over the direct binding this route already
  uses.
- **`streamSimple`** (`packages/ai/src/api/openai-completions.ts`) — not used. It drives the OpenAI
  SDK client against a real HTTPS endpoint (`model.baseUrl`) with an API key, using `ChatCompletionChunk`
  parsing built for an actual OpenAI-compatible wire response. `src/model-route.ts`'s whole design is a
  direct Workers AI *binding* call with no credential and no endpoint reachable from outside the
  route (`FORBIDDEN_FIELDS` blocks `endpoint`/`provider`/`credentials`); reusing `streamSimple` would
  mean reintroducing exactly the credential/endpoint surface the route exists to remove. Pi's own
  built-in `cloudflare-workers-ai` provider (`packages/ai/src/providers/cloudflare-workers-ai.ts`) has
  the same problem: it calls Cloudflare's REST API over HTTPS with a `CLOUDFLARE_API_KEY`, not the
  binding.

None of the three fit a binding-only, credential-free streaming call, so `model-route-stream.ts`
hand-rolls a minimal SSE line parser scoped to exactly that seam (`env.AI.run(model, { ...,
stream: true })`'s raw byte stream), translating it into this route's own closed `ModelStreamEvent`
union before anything else in the system sees it.

## Design

**Two production paths coexist in `ModelCapability` on purpose.** `runStream` is the real path:
`route-stream.ts`'s `createRouteStreamFn` is what `facet-turn.ts` wires as `capabilities.MODEL`'s
`streamFn` for Pi's `Agent` (confirmed: `facet-turn.ts` calls
`createRouteStreamFn(capabilities.MODEL, signal)`, not the buffered `runGeneration0Turn`/`turn.ts`
path). `run` is kept, byte-for-byte unchanged, only because `turn.ts`/`request-handler.ts` — T7-owned
files outside this task's scope — still call it for the hand-written buffered loop T7's own
acceptance criteria already commit to deleting. Changing `ModelCapability`'s shape at all forced
`test/facet/generation-0/fakes.ts` and `facet-turn-helpers.ts` to add a matching `runStream` (both
files implement the interface), which is why they appear in the changed-paths table despite not
being in T4's listed scope; the alternative was breaking T7's and other tasks' existing tests to stay
inside a stricter interpretation of scope. Report to T7: once `runGeneration0Turn` and its callers
are deleted, `ModelCapability.run`, `ModelInference`, and `ModelRoute.run` become deletable too — the
`@deprecated` doc comment on `ModelRoute.run` and `capabilities.ts` say so explicitly.

**The wire format between `ModelRoute.runStream` and `route-stream.ts` is this route's own plain
NDJSON protocol, not Workers AI's raw SSE.** `model-route-stream.ts` parses whatever Workers AI's
binding actually emits and re-encodes it as one JSON object per line from a closed union
(`text-delta`, `tool-call-delta`, `done`, `error`) — plain values only, consistent with ADR-0035's
rule for anything crossing a Worker RPC boundary. This means `route-stream.ts` and
`workers-ai-adapter.ts` need not know or trust the provider's exact JSON shape; only
`model-route-stream-parse.ts` does, and it degrades (ignores an unrecognized field) rather than
throwing, because a provider detail this route does not model must not fail an otherwise-good turn.

**Tool-call argument deltas are treated as fragments to concatenate, not full-string snapshots.**
`ToolCallDelta.argumentsDelta` is appended to a per-index accumulator; the accumulated text is
parsed as JSON only when a turn actually needs the result (the final `done` message, or a UI's
best-effort mid-stream display) and falls back to `{}` on invalid/partial JSON rather than throwing.
This is deliberately robust to either resolution of the acceptance criterion 1 empirical question
(below): a provider that streams fragments concatenates correctly, and a provider that reports the
whole arguments string in one final chunk also concatenates correctly (one fragment instead of
several).

## Acceptance criteria

**1. Preserve one immutable model selection and credential holder; prove the route supports the
required text/tool stream in the paid runtime, or record a concrete limitation; no synthetic token
chunks; no provider picker.**
Partially holds, with an explicit unresolved paid-proof, per the task's own "paid clause lifted out"
section: *"T4.1's paid proof belongs to T1b, blocked awaiting owner approval... write the assumption
down, mark it unverified."* `MODEL`/`REASONING_EFFORT` stay the single fixed constants in
`model-route.ts`, untouched. No synthetic chunks are substituted anywhere: every `text-delta`/
`tool-call-delta` event carries only text this route actually decoded from the provider's own
stream. **Unverified, recorded honestly, not resolved:** whether
`@cf/zai-org/glm-5.3-flash`'s Workers AI binding stream with `stream:true` (a) yields incremental
`tool_calls` fragments or only a complete `tool_calls` array in one final chunk, and (b) what its
exact JSON chunk shape is (Workers AI's classic `{ response }` per-token shape vs. an
OpenAI-chat-completions-chunk shape). `model-route-stream-parse.ts`'s doc comment states this
explicitly and the parser is written to produce a correct result under either hypothesis (see
Design, tool-call fragments). **Blocked: awaiting owner approval for a paid probe** to settle which
hypothesis is real; nothing here fakes that proof.

**2. The adapter delivers actual incremental text, tool-call assembly, terminal status, and model
errors through Pi's event types; tests cover split UTF-8, split tool arguments, a truncated
provider stream, provider error, and cancellation; cancellation prevents further model calls and
releases the reader; document whether it can stop an already-issued inference.**
Holds. `test/model-route-stream.test.ts`: `"delivers incremental text deltas..."`,
`"assembles a tool call whose arguments arrive split across several chunks"`,
`"reassembles a multi-byte UTF-8 character split across two raw byte chunks"` (splits the two-byte
UTF-8 encoding of "é" itself across two raw `Uint8Array` reads),
`"a provider stream that never sends a terminal marker becomes an error event"` (truncated stream),
`"a provider call that rejects before any bytes arrive becomes an error event"` (provider error).
`test/facet/generation-0/route-stream.test.ts`: `"streams incremental text..."`,
`"streams a tool call and assembles its parsed arguments"` (both verified through Pi's real
`start`/`text_*`/`toolcall_*`/`done` event sequence, not just the final message),
`"a provider stream that ends mid-turn without a result fails the turn but keeps the partial
text"` (mid-stream failure, explicitly required by the brief), `"an already-aborted signal stops
the model from being called at all"`, and `"aborting mid-stream releases the reader and stops
applying further events"` (asserts `model.calls` stays at 1 — no further model call — and that
text pushed after the abort never reaches the assembled message). Documented in
`createRouteStreamFn`'s doc comment: cancellation stops this route from reading further chunks and
calling the model again, but **cannot** stop an already-issued Workers AI inference — the binding's
`AiOptions` type has no `signal`/abort field, so there is no first-class way to cancel a call already
in flight; the comment states this explicitly rather than implying otherwise.

**3. Parse untrusted model request/tool definitions and provider outputs at this seam; no
arbitrary endpoint/model/provider credential/generation-control capability can pass through; bound
input and event bytes using bytes rather than string length.**
Holds. `validateRequest`'s `FORBIDDEN_FIELDS` check (unchanged) still blocks `model`,
`reasoning_effort`, `credentials`, `endpoint`, `provider` on the request side — verified by the
existing `test.each(["model", "reasoning_effort", "credentials", "endpoint", "provider"])` test,
still passing unmodified. The provider's own stream output is now also parsed defensively:
`model-route-stream-parse.ts`'s `parseProviderChunk` and its helpers use the same
`asUntrusted`/`field`/`hasOwn` narrowing `validateRequest` uses (now exported from `model-route.ts`
for that reuse), never trusting a field's type without a runtime check. Byte bounds: `validateRequest`'s
1 MiB request bound now measures `new TextEncoder().encode(JSON.stringify(raw)).length` instead of
`JSON.stringify(raw).length` (UTF-16 code units) — proven by
`"rejects a request whose UTF-8 byte size exceeds 1 MiB even though its string length does not"`
(600,000 "é" characters: 600,000 UTF-16 code units, under the limit, but 1,200,000 UTF-8 bytes, over
it) and the paired accepts-under-limit test. The provider's own output stream is separately bounded
by `MAX_STREAM_EVENT_BYTES` (8 MiB) counted on raw `Uint8Array.byteLength`, not decoded string
length, in `readSseLines`.

**4. Expose fixed non-secret context/output limits Pi needs; carry real usage if provided,
otherwise represent unavailability with a documented conservative estimate; never claim zero usage
is a measurement; existing text/tool history stays readable.**
Holds for usage; `ROUTE_MODEL.contextWindow`/`maxTokens` deliberately left at `0`, per this task's
own "Flag, do not fix" instruction (see below). `resolveUsage` in `model-route-stream.ts` carries
the provider's own `prompt_tokens`/`completion_tokens` (or `input_tokens`/`output_tokens`) through
unchanged when a chunk reports them (`estimated: false`), proven by
`"carries real provider usage through instead of estimating it"`. When the provider reports none,
it computes a documented conservative byte-based estimate (`~1 token per 3 UTF-8 bytes`, which
over-estimates rather than under-estimates token count) instead of asserting zero, proven by
`"estimates non-zero usage, and marks it as an estimate, when the provider reports none"`
(`estimated: true`, both token counts `> 0`). `toPiUsage` in `stream-assembler.ts` carries these
numbers into Pi's `AssistantMessage.usage.input`/`.output`/`.totalTokens`; `cacheRead`/`cacheWrite`/
`cost` stay `0` because this generation never attempts prompt caching and has no real cost data —
not a second silent-zero claim, an accurate report of a feature this generation does not use.
Existing text/tool history: `piContextToRouteRequest`/`routeResponseToPiAssistant` in
`workers-ai-adapter.ts` are unchanged and their whole test file (`adapter.test.ts`, 17 tests) still
passes unmodified.

**5. Keep transport envelopes plain across Workers RPC; tests use the real loaded seam as well as a
deterministic provider adapter.**
Holds. `ModelRoute.runStream` returns `ReadableStream<Uint8Array> | ValidationFailure` — plain bytes
or a plain object, matching `MainFacetTarget.startTurn`'s existing precedent for streaming across
this same kind of RPC boundary (ADR-0035). Every `ModelStreamEvent` is a JSON-serializable
discriminated union with no class instances. Real loaded seam:
`test/facet/generation-0/loaded-facet-turn-entry.ts` is a genuine `esbuild`-bundled Worker Loader
fixture (`tools/build-loaded-execution-env-fixture.mts`), and its scripted route's new `runStream`
method is what `test/facet/generation-0/facet-turn-loaded.test.ts` (6 tests, all passing) exercises
through a real `WorkerLoader`/RPC round trip, not an in-process object. Deterministic provider
adapter: `test/model-route-stream.test.ts` and `test/facet/generation-0/route-stream.test.ts`, both
new, cover the seam with fully scripted fakes.

## Kept properties

- `FORBIDDEN_FIELDS` unchanged; still blocks `model`, `provider`, `endpoint`, `credentials`,
  `reasoning_effort` on every request, streaming or buffered.
- `MODEL` and `REASONING_EFFORT` remain the sole fixed constants; nothing added a model-selection
  parameter or a second model identity.
- `endedStream`/`failedStream`-equivalent termination (`TurnAssembler.fail`) is exercised for a
  mid-stream failure specifically, not only a pre-start one — the explicit test the brief asked for:
  `"a provider stream that ends mid-turn without a result fails the turn but keeps the partial
  text"`.

## What was deliberately NOT done

- **Did not touch `wrangler.jsonc`, an AI Gateway, or `src/worker.ts`.** Adopting
  `createGatewayBindingFetch` would have required provisioning an AI Gateway resource, which is
  infra/config outside this task's listed scope and outside tonight's no-paid-spend constraint.
- **Did not touch `src/facet/generation-0/{turn,request-handler}.ts`** (T7-owned) or delete
  `runGeneration0Turn`/the old `/turn` handler, even though they are now the *only* callers of the
  buffered `ModelCapability.run`/`ModelRoute.run`/`ModelInference`/`invokeModel`. T7's own acceptance
  criteria already commit to deleting them; flagged above and in the relevant doc comments (marked
  `@deprecated`) so T7 can remove both sides together.
- **Did not change `ROUTE_MODEL.contextWindow`/`maxTokens` from `0`.** Per this task's explicit
  "Flag, do not fix" instruction. Flag for T7 (also restated in `stream-assembler.ts`'s doc comment
  on `ROUTE_MODEL`): a zero context window may make Pi's compaction trigger unreachable; T7 must
  confirm what Pi actually does with a zero window before claiming a forced-compaction test passes
  (goal criterion 5).
- **Did not rewrite `workers-ai-adapter.ts`.** Its existing pure functions already did exactly what
  the new incremental assembly needs for building the one request and the final assembled message;
  duplicating that logic would have been the "third adapter" the brief warned against.
- **Did not attempt exact content-array index parity between mid-stream partial snapshots and the
  final assembled message's canonical order** (text block first if present, then tool calls, per
  `normalizeResponse`'s existing aggregation) for the rare case of genuinely interleaved
  text/tool-call streaming within one turn. `TurnAssembler` tracks blocks in arrival order for
  progressive `_start`/`_delta`/`_end` events (a UI/progress concern), while the authoritative `done`
  message Pi's agent loop actually records always comes from `routeResponseToPiAssistant`'s existing,
  tested canonical assembly. A real interleaved-then-reordered turn would only affect the fidelity
  of intermediate progress events, never the turn's correctness.
